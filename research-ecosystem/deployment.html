Deployment

Website, Server, and Hosting Map

The current site is a GitHub Pages static website. That is enough for public pages, repository-backed JSON, PubMed search from the browser, and GitHub Issues. A server becomes necessary when the site needs secrets, accounts, databases, scheduled jobs, or private APIs.

Short Answer For This Website

I can keep building the current website without VS Code and without a traditional server. GitHub is the source folder, GitHub Pages is the public website, and Codex can edit, validate, commit, and upload the files. VS Code is optional for you: useful if you want to open files yourself, but not required for me to keep working.

Vercel becomes useful when we want server-side code, protected environment variables, OpenAI API calls, PubMed enrichment that should not run in the browser, login, or deployment previews. Supabase becomes useful when the website needs a real private database, user accounts, file storage, or per-user permissions.

Now

GitHub Pages

Publishes HTML, CSS, JavaScript, images, and JSON directly from the repository.

  • Good for public research notes and dashboards.
  • Can call public APIs such as PubMed from the browser.
  • Cannot safely store private API keys or user secrets.
Next

Vercel

Adds serverless API routes and automatic deploy previews from GitHub.

  • Good for OpenAI API calls, protected PubMed enrichment, and backend helpers.
  • Stores environment variables outside public website code.
  • Still keeps GitHub as the source of truth.
Data

Supabase

Adds database, login, file storage, and row-level permissions when the site becomes private or collaborative.

  • Good for personal literature libraries and research logs.
  • Can support private notes that should not live in a public repository.
  • Works well beside Vercel APIs.

What Codex Can Do

Codex can write the frontend, backend API routes, database schema, deployment configuration, validation scripts, GitHub Issues, and documentation. You still approve account-level actions: GitHub permissions, Vercel project connection, Supabase project creation, billing choices, and secret values.

Decision Checklist

  1. If the feature is a public page, public JSON, local browser tool, PubMed search, or downloadable HTML note, keep it on GitHub Pages.
  2. If the feature needs an API key, OpenAI call, background processing, or protected request, add Vercel API routes.
  3. If the feature needs login, private notes, editable records from multiple devices, or file uploads, add Supabase.
  4. If the feature needs both AI and private saved data, use Vercel for server logic and Supabase for data.

Research Site Upgrade Path

  1. Now: keep PubMed search, literature queue, deep-reading templates, knowledge maps, and project dashboards on GitHub Pages.
  2. Next: connect Vercel so the site can call protected AI services without exposing keys in the browser.
  3. Then: connect Supabase for a private literature database, saved reading history, login, and uploaded PDFs.
  4. Later: add scheduled jobs to refresh PubMed searches, create GitHub Issues, and prepare weekly research digests.

When To Upgrade

  1. Stay on GitHub Pages while the site is public, static, and repository-backed.
  2. Add Vercel when we need secure server-side API calls or environment variables.
  3. Add Supabase when we need login, private records, database queries, or file storage.
  4. Keep GitHub Issues and the project dashboard as the planning layer throughout.
