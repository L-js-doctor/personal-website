AI Translation

Real Translation API Plan

The current website can search PubMed and generate translation-ready reading artifacts in the browser. The next real upgrade is a protected backend API that sends abstracts, notes, or selected papers to an AI or translation service without exposing private keys in public website code.

Short Answer

Yes, this site can connect to real translation APIs. The safe path is GitHub Pages for the visible website, Vercel or Cloudflare Worker for protected API routes, OpenAI for literature deep reading and structured translation, and optional DeepL for pure high-quality translation. PubMed stays as the literature data source.

01

Browser

The page collects the paper title, PMID, abstract, reading goal, and target language.

  • Good for forms, search results, previews, downloads, and local export.
  • Should not contain OpenAI, DeepL, or NCBI private API keys.
02

Backend API

A Vercel API route or Cloudflare Worker receives the request, checks size, adds prompts, and calls the external provider.

  • Stores keys as environment variables.
  • Can limit request rate, log errors, and normalize output.
03

Provider

OpenAI or DeepL returns translated text, structured reading notes, or JSON fields for the website.

  • OpenAI is best for reasoning, summaries, methods, limitations, and study design extraction.
  • DeepL is best when the task is mostly direct translation.

How The Data Would Flow

  1. User searches PubMed or pastes a paper abstract in Literature Lab.
  2. User chooses output language: Chinese, English, Japanese, Russian, or German.
  3. The browser sends only the selected paper data to our protected backend endpoint. If the visible site stays on GitHub Pages, paste the Vercel or Cloudflare Worker endpoint URL into the Literature Lab endpoint setting.
  4. The endpoint calls OpenAI for deep reading, DeepL for direct translation, or both if needed.
  5. The site receives structured output and lets the user export Markdown, JSON, or HTML.

Recommended First Build

  1. Use Vercel if account login works; otherwise create a Cloudflare Worker.
  2. Use one endpoint: /api/deep-read on Vercel, or the Worker URL from api/deep-read-worker.js.
  3. Store OPENAI_API_KEY in the host's secret environment variables.
  4. Optional: set OPENAI_MODEL if we want to change the default model without editing code. The scaffold defaults to gpt-5.5.
  5. Send title, abstract, PMID, goal, and target language from the Literature Lab form.
  6. Return a strict JSON object with summary, introduction, hypothesis, design, methods, results, mechanism, limitations, and follow-up search terms.
  7. Add buttons on the website: Translate, Deep read, Export HTML, Export JSON.

Current Project Scaffold

The repository now includes api/deep-read.js, a deployable Vercel serverless function, and api/deep-read-worker.js, a Cloudflare Worker fallback. Both call OpenAI from the server, ask for a strict literature deep-reading JSON object, and keep the API key out of public browser code. The Literature Lab has an AI deep read button that calls this endpoint when the site is hosted with the backend. If the frontend remains on GitHub Pages, the Literature Lab can save a Vercel endpoint such as https://your-project.vercel.app/api/deep-read or a Worker endpoint such as https://ljsdoctor-deep-read-worker.your-subdomain.workers.dev in browser storage. The same endpoint also supports a simple GET health check so the page can test whether the backend is online and whether OPENAI_API_KEY is configured.

Provider Choice

  • OpenAI first: best fit for this site because the goal is not only translation; it also needs paper triage, experimental design extraction, and structured literature notes.
  • DeepL optional: add later if you want polished direct translation of long paragraphs or finished notes.
  • NCBI API key optional: useful only if PubMed usage grows beyond basic browser searching or needs higher request limits.

What You Would Need To Provide

  1. A Vercel account connected to GitHub, or a Cloudflare account for the Worker fallback.
  2. An OpenAI API key for real AI deep reading and translation.
  3. Optional: a DeepL API key for direct translation quality.
  4. Optional: an NCBI API key if the PubMed connector becomes high-volume.

These keys should be pasted only into the hosting provider's secret settings, not into website files, chat messages that will be committed, or public GitHub code.

Deployment Checklist

  1. Use Vercel if login is available, or create a Cloudflare Worker if Vercel remains blocked.
  2. For Vercel, confirm it sees vercel.json and api/deep-read.js.
  3. For Cloudflare Worker, paste api/deep-read-worker.js into a Worker named ljsdoctor-deep-read-worker.
  4. Add OPENAI_API_KEY in the backend environment variables or Worker secrets.
  5. Optional: add OPENAI_MODEL, matching the template in .env.example.
  6. Optional but recommended: add ALLOWED_ORIGIN=https://l-js-doctor.github.io to limit browser calls to the public site.
  7. Deploy, then test /api/deep-read through the Literature Lab endpoint test button.
  8. For a command-line check, run tools/test-ai-endpoint.ps1 with the deployed endpoint URL.
  9. If the frontend remains on GitHub Pages, paste the full backend API URL into the AI endpoint setting.

For a click-by-click setup guide, open Vercel Connection Checklist.

Why This Cannot Be Just Frontend

GitHub Pages publishes static files. Anyone can view the JavaScript sent to their browser. If a private API key is placed there, it becomes public. A backend route solves this by keeping the key on the server, while the website calls only our own safe endpoint.
